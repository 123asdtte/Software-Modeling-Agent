【AI辅助状态机图建模】

在前述任务实现中，已通过手工方式完成了预警信息全生命周期管理状态机图的绘制。本节进一步探讨如何将AI工具融入状态机图建模流程，形成“以建模者为核心、AI辅助执行”的高效协作模式。

需要明确的是，AI无法替代建模者进行对象生命周期边界的判定、状态粒度的把控以及事件驱动逻辑的语义辨析，它的价值在于快速将建模者的分析结论转化为规范图形、检查语法一致性，并提供初稿框架。在此建议采用四步迭代法，将AI工具嵌入状态机图建模的各环节。

第一步：手工前置分析

建模者在草稿纸上完成以下三项工作：

①识别核心对象及其生命周期边界：明确需要建模的反应型对象（如“预警信息”“漏洞处置任务”“推送任务”），划定其从创建到销毁/归档的完整生命周期范围；

②提取关键状态：逐条梳理对象在其生命周期中所处的稳定阶段，区分简单状态与复合状态（顺序/并发），并标注初始状态与最终状态；

③定义转换与触发事件：初步标注各状态之间的转换关系，明确每个转换的触发事件（调用事件、变化事件、时间事件、信号事件）、监护条件（如有）以及伴随执行的动作。

第二步：提交初始提示词

第一次提交给AI的提示词需包含对象名称、核心状态列表、状态转换关系及触发事件说明，无需罗列全部业务细节。过长的提示词既增加输入成本，也不利于后续迭代调整。表7-3列出了推荐提示词结构。

表7-3　状态机图建模初始提示词结构

| 信息类型 | 说明 | 示例 |
| --- | --- | --- |
| 对象名称 | 明确建模的核心对象 | AI学业预警平台——预警信息 |
| 核心状态列表 | 按生命周期顺序列出所有状态 | 预警草稿待生成、已生成待审核、审核驳回待重制、审核通过待推送、已推送教师待确认、已确认待推送学生、学生已接收待反馈、已反馈待评估、预警闭环已归档、预警已暂停挂起 |
| 状态转换关系 | 说明状态之间的转换及触发事件 | 预警草稿待生成→已生成待审核（规则匹配命中）；已生成待审核→审核通过待推送（审核通过）；已生成待审核→审核驳回待重制（审核驳回）；已推送教师待确认→已确认待推送学生（教师确认）；已确认待推送学生→学生已接收待反馈（推送成功）；学生已接收待反馈→已反馈待评估（学生提交反馈）；已反馈待评估→预警闭环已归档（评估完成）；任意状态→预警已暂停挂起（中断挂起）；预警已暂停挂起→恢复前状态（恢复预警） |

对于AI学业预警平台预警信息全生命周期管理，初始提示词可设置如下：

请为AI学业预警平台——智能预警与成长干预模块的“预警信息”对象生成PlantUML状态机图。该对象是平台的核心反应型对象，其生命周期从预警草稿生成到归档闭环。状态包括：预警草稿待生成、已生成待审核、审核驳回待重制、审核通过待推送、已推送教师待确认、已确认待推送学生、学生已接收待反馈、已反馈待评估、预警闭环已归档、预警已暂停挂起。转换关系如下：预警草稿待生成→已生成待审核（触发事件：规则匹配命中）；已生成待审核→审核通过待推送（触发事件：审核通过）；已生成待审核→审核驳回待重制（触发事件：审核驳回）；审核驳回待重制→预警草稿待生成（触发事件：重新生成）；审核通过待推送→已推送教师待确认（触发事件：推送教师）；已推送教师待确认→已确认待推送学生（触发事件：教师确认）；已确认待推送学生→学生已接收待反馈（触发事件：推送学生）；学生已接收待反馈→已反馈待评估（触发事件：学生提交反馈）；已反馈待评估→预警闭环已归档（触发事件：评估完成）；预警闭环已归档为最终状态，生命周期结束。支持异常处理：任意状态均可通过“中断挂起”事件进入“预警已暂停挂起”状态；处于“预警已暂停挂起”状态时，通过“恢复预警”事件返回中断前状态（使用浅历史状态H记录中断前位置）。要求：使用初始伪状态（●）标识生命周期起点；使用最终状态（◉）标识生命周期终点；状态转换箭头上标注触发事件名称；暂停挂起场景使用浅历史状态（H）实现断点恢复。

将该提示词提交给AI后，可获得初版PlantUML代码或图形化输出。此阶段得到的是建模初稿，需进入下一步进行人工校验。

第三步：对AI输出进行系统化质检

AI输出的初稿必须经过人工校验，校验依据是本任务7.1节和7.2节的核心知识点，而非主观感受。这包括三个方面的检验，可按表7-4、表7-5和表7-6所列的标准与操作方法逐项开展。

表7-4　状态与生命周期校验表

| 检查项 | 判定标准 | 不通过时的处理 |
| --- | --- | --- |
| 核心对象是否明确 | 状态机图应围绕单一反应型对象构建，所有状态均属于该对象的生命周期 | 明确标注状态机所属的对象名称 |
| 状态是否覆盖完整生命周期 | 状态集合应从对象的创建起始覆盖至销毁/归档终止，无遗漏阶段 | 补充遗漏的状态（如异常处理、暂停挂起等分支状态） |
| 是否存在粒度过细的状态 | 状态应为对象生命周期中的稳定阶段，不应与动作节点混淆（如“正在执行XXX操作”应建模为动作而非状态） | 将粒度过细的状态合并或调整为复合状态内部子状态 |
| 初始状态与最终状态是否正确 | 每个状态机应有一个初始伪状态（●）；应有至少一个最终状态（◉）标识生命周期终点 |  |

表7-5　复合状态与历史状态校验表

| 问题类型 | 典型表现 | 处理方式 |
| --- | --- | --- |
| 顺序复合状态使用不当 | 将本应顺序执行的子状态误建为并发区域，或反之将并发逻辑简化为顺序状态 | 检查子状态之间是否存在先后依赖关系：若是，使用顺序复合状态；若相互独立且可并行，使用并发复合状态（虚线分隔正交区域） |
| 并发复合状态区域划分不清 | 并发区域内的子状态未各自配备独立的初始伪状态和最终状态 | 为每个并发区域补充独立的初始伪状态（●）和最终状态（◉） |
| 历史状态误用或遗漏 | 在不需要断点续办的场景中滥用历史状态，或在需要恢复中断的场景中遗漏历史状态 | 若存在中断/恢复逻辑且需记忆中断位置，添加浅历史状态（H）；若需记忆多层嵌套中断位置，使用深历史状态（H*） |

表7-6　转换逻辑校验表

| 控制逻辑类型 | 判定依据 | 检验方法 |
| --- | --- | --- |
| 事件触发完整性 | 每个转换均应有明确的触发事件（调用事件、变化事件、时间事件、信号事件之一），无“无源触发”的转换 | 检查每个转换箭头是否标注了触发事件；是否存在未标注任何触发器的事件缺失转换 |
| 监护条件正确性 | 监护条件为布尔表达式，仅在触发事件发生时求值，且同一事件触发的多个转换应具备互斥的监护条件 | 检查监护条件语法是否为布尔表达式；检查同一源状态相同事件触发不同目标状态时，监护条件是否互不重叠 |
| 动作标注规范 | 转换触发的伴随动作应以斜杠“/”引导标注在转换箭头上，格式为“事件触发 [监护条件] / 动作” | 检查是否存在动作未以“/”引导标注；检查动作是否为原子计算（赋值、调用、创建、销毁、发送信号等） |
| 转换目标合法性 | 所有转换的目标状态应为已定义状态，不存在指向未定义状态的“悬空转换” | 核对每个转换的终点是否与状态列表中的状态一一对应 |

第四步：定向迭代

当校验发现问题时，无需重新提交全部需求，只需针对具体问题向AI发送分条、明确的修改指令。每次修正后再次执行第三步校验，直至状态机图与需求完全一致。修改指令可参考以下写法：

请对当前状态机图做以下三处调整：

将“预警草稿待生成”→“已生成待审核”的转换触发事件标注为“规则匹配命中”；

在“已生成待审核”与“审核通过待推送”之间增加监护条件“审核等级≥3级”，并在“已生成待审核”与“审核驳回待重制”之间增加监护条件“审核等级<3级”；

在“预警已暂停挂起”状态内部添加浅历史状态（H），并将“恢复预警”转换的终点指向该历史状态。

迭代终止条件：当三步校验全部通过，且状态机图能够完整、准确地反映对象生命周期行为时，建模工作即告完成。
