【AI辅助活动图建模】

在前述任务实现中，已通过手工方式完成了智能预警与成长干预模块活动图的绘制。本节进一步探讨如何将AI工具融入活动图建模流程，形成“以建模者为核心、AI辅助执行”的高效协作模式。

需要明确的是，AI无法替代建模者进行业务流程边界的判定、动作粒度的把控以及并行/分支逻辑的语义辨析，它的价值在于快速将建模者的分析结论转化为规范图形、检查语法一致性，并提供初稿框架。在此建议采用四步迭代法，将AI工具嵌入活动图建模的各环节。

第一步：手工前置分析

建模者在草稿纸上完成以下三项工作：

①识别流程参与角色：明确业务流程涉及的所有责任主体（人员、系统、外部实体），对照任务六中的6.2.7分区（泳道）划分原则进行归类；

②提取核心动作节点：逐条梳理业务流程中的具体操作步骤，区分原子动作（如“采集教务系统学业成绩”）与复合活动（如“多源数据融合”）；

③标注控制逻辑：初步标注各动作节点之间的控制关系，包括顺序流转、条件分支（决策节点）、并行执行（分叉/汇合节点）以及跨分区控制流。

第二步：提交初始提示词

第一次提交给AI的提示词需包含系统/模块名称、参与角色清单、核心动作节点列表以及明确的控制逻辑说明，无需罗列全部业务细节。过长的提示词既增加输入成本，也不利于后续迭代调整。表6-1列出了推荐提示词结构。

表6-1　活动图建模初始提示词结构

| 信息类型 | 说明 | 示例 |
| --- | --- | --- |
| 模块名称 | 明确建模对象 | AI学业预警平台——智能预警与成长干预模块 |
| 参与角色清单 | 列出已识别的全部责任主体（泳道） | 定时任务调度器、AI推演与决策引擎、授课教师/辅导员、学生 |
| 核心动作节点 | 按执行顺序列出所有动作 | 触发多源数据采集任务；采集教务系统学业成绩；采集智慧校园行为数据；采集学生管理系统基础信息；汇总采集数据；融合多源数据；生成学生学习画像；预警规则匹配判定；生成预警信息；生成归因分析报告；生成干预方案；接收预警通知与干预方案；修改干预方案；确认干预方案；推送预警通知给学生；接收预警通知；查看预警详情；提交预警反馈；接收学生预警反馈；记录帮扶信息；完成智能评估；更新学生学习画像与干预记录 |
| 明确的控制逻辑 | 说明顺序、分支、并行、跨分区关系 | 采集任务由定时任务调度器触发后，AI引擎分叉为三路并行采集；三路汇合后依次执行融合、画像、规则匹配、预警与方案生成；教师接收方案后决策是否修改；学生端接收推送并提交反馈；反馈经教师处理后回传AI引擎更新画像 |

对于智能预警与成长干预模块，初始提示词可设置如下：

请为AI学业预警平台——智能预警与成长干预模块生成PlantUML活动图。参与者（泳道）包括：定时任务调度器、AI推演与决策引擎、授课教师/辅导员、学生。动作节点按执行顺序包括：触发多源数据采集任务、采集教务系统学业成绩、采集智慧校园行为数据、采集学生管理系统基础信息、汇总采集数据、融合多源数据、生成学生学习画像、预警规则匹配判定、生成预警信息、生成归因分析报告、生成干预方案、接收预警通知与干预方案、修改干预方案、确认干预方案、推送预警通知给学生、接收预警通知、查看预警详情、提交预警反馈、接收学生预警反馈、记录帮扶信息、完成智能评估、更新学生学习画像与干预记录。控制逻辑说明：定时任务调度器触发采集后，AI引擎分叉为三路并行采集教务成绩、行为数据、基础信息；三路汇合后先执行 “汇总采集数据” ，再顺序执行融合、画像生成、规则匹配、预警信息生成、归因分析报告生成、干预方案生成；干预方案跨分区传递给教师，教师决策“是否需要修改干预方案”——若需要修改则执行“修改干预方案”，若无需修改则执行“确认干预方案”；确认后跨分区推送预警通知给学生；学生依次执行接收通知、查看详情、提交反馈；反馈跨分区回传教师，教师执行记录帮扶信息、完成智能评估；评估结果跨分区回传AI引擎执行更新画像与干预记录，最后流程终止。要求：使用泳道清晰划分四个责任分区；分叉节点与汇合节点成对出现；决策节点须标注监护条件“[需要修改干预方案]”和“[无需修改干预方案]”。

将该提示词提交给AI后，可获得初版PlantUML代码或图形化输出。此阶段得到的是建模初稿，需进入下一步进行人工校验。

第三步：对AI输出进行系统化质检

AI输出的初稿必须经过人工校验，校验依据是本任务6.1节和6.2节的核心知识点，而非主观感受。这包括三个方面的检验，可按表6-2、表6-3和表6-4所列的标准与操作方法逐项开展。

表6-2　分区（泳道）校验表

| 检查项 | 判定标准 | 不通过时的处理 |
| --- | --- | --- |
| 所有参与者是否均有独立分区 | 每个责任主体应有对应的泳道 | 补充遗漏的分区 |
| 动作节点是否归属正确分区 | 每个动作节点应放置在所属责任主体的分区内 | 将错放的动作节点移至正确分区 |
| 是否有内部组件被误列为分区 | 数据库、消息队列等内部组件不属于活动图泳道 | 从分区列表中删除或调整为对象节点 |
| 控制流是否可跨分区流转 | 跨分区控制流应使用带箭头的实线表示 | 检查跨分区连接线的正确性 |

表6-3　动作粒度校验表

| 问题类型 | 典型表现 | 处理方式 |
| --- | --- | --- |
| 粒度过细 | 动作为单一界面操作，如“点击确认按钮”“输入网址” | 合并至上层动作或删除 |
| 粒度过粗 | 一个动作覆盖多个独立业务步骤，如“完成预警全流程” | 拆分为多个独立动作节点 |
| 遗漏关键动作 | 流程描述中有明确步骤但图中缺失 | 补充遗漏的动作节点 |

表6-4　控制逻辑校验表

| 控制逻辑类型 | 判定依据 | 检验方法 |
| --- | --- | --- |
| 顺序流转 | 动作节点之间存在明确的先后执行依赖关系，前一动作完成后控制流自动传递至后一动作 | 检查相邻动作节点之间是否通过控制流正确连接；检查是否存在未连接任何控制流的孤立动作节点 |
| 条件分支 | 决策节点输出两条及以上分支，每条分支标注互斥的监护条件，确保任一执行场景下均有且仅有一条有效路径 | 检查决策节点的各输出分支是否均标注了监护条件；检查各分支监护条件是否互不重叠；检查是否配置了“[else]”兜底分支以保证条件完备性 |
| 分支汇合 | 多条替代路径通过合并节点汇聚为单条控制流，合并后统一执行后续流程 | 检查决策节点与合并节点是否配套使用；检查合并节点的输入分支是否覆盖了决策节点的所有输出分支 |
| 并行分叉 | 分叉节点将单条控制流拆分为多条可同时执行的并行分支，各分支独立执行、互不阻塞 | 检查分叉节点的输出分支数量与对应汇合节点的输入分支数量是否一致；检查各并行分支是否均以控制流正确连接到汇合节点 |
| 并行同步 | 汇合节点等待所有并行分支全部到达后才向下流转，任意分支未完成则整体等待 | 检查所有并行分支是否最终汇聚至同一汇合节点；检查是否存在因分支数量不匹配导致流程永久阻塞的风险 |
| 数据传递 | 动作之间通过对象流传递业务对象或数据值，对象节点准确表示流程中流动的数据实体 | 若建模时选择补充对象流，检查对象节点是否连接在正确的产出动作与消费动作之间；核实对象节点命名是否符合“对象名:类型名”的规范格式；若未使用对象流，本项校验可跳过 |

第四步：定向迭代

当校验发现问题时，无需重新提交全部需求，只需针对具体问题向AI发送分条、明确的修改指令。每次修正后再次执行第三步校验，直至活动图与需求完全一致。修改指令可参考以下写法：

请对当前活动图做以下三处调整：

将“推送预警通知给学生”动作节点从“授课教师/辅导员”分区移至“学生”分区；

在“预警规则匹配判定”与“生成预警信息”之间补充对象节点“匹配结果:匹配结果对象”及对应的对象流；

将决策节点“是否需要修改干预方案”的两条输出分支监护条件分别标注为“[需要修改干预方案]”和“[无需修改干预方案]”。

迭代终止条件：当三步校验全部通过，且活动图能够完整、准确地反映业务流程需求时，建模工作即告完成。

迭代终止条件不是“AI认为生成完成”，而是建模者确认模型同时满足业务需求和 UML 建模规范。
