# 开发流程与规范总则（v13）

> 适用范围：AI教学智能体平台 v13 全部开发活动。
> 原则：**所有开发前先读本目录规范；所有改动可追溯；所有产物可评审；不依赖 v12 代码、不迁移扣子工作流，扣子版仅作目标效果参考。**

---

## 1. 开发流程总览

```
需求确认 → 文档先行 → 设计评审 → 编码实现 → 自测 → 代码评审 → 联调 → 验收 → 发布
```

| 阶段 | 入口条件 | 出口条件 | 负责 |
|---|---|---|---|
| 需求确认 | 用户/老师提出需求 | 需求文档（PRD）评审通过 | 产品/项目负责人 |
| 文档先行 | PRD 通过 | 技术方案 / 详细设计完成 | 开发负责人 |
| 设计评审 | 技术方案完成 | 评审意见闭环 | 全体 + 老师 |
| 编码实现 | 设计通过 | 代码完成 + 自测通过 | 开发 |
| 代码评审 | 自测通过 | 评审无阻塞项 | 至少 1 名其他开发者 |
| 联调验收 | 评审通过 | 按验收标准逐项通过 | 全体 |
| 发布 | 验收通过 | 可演示 / 可上线版本 | 项目负责人 |

**硬性要求**：不允许"边写代码边补文档"；未评审的设计不得进入编码阶段。

## 2. 需求管理规范

- 一切需求以 PRD 为准，口头需求必须落成 PRD 变更。
- PRD 必须包含：背景 / 用户故事 / 功能描述 / 输入输出 / 边界与例外 / 验收标准。
- 需求变更流程：提出变更 → 评估影响（范围/工期/风险）→ 更新 PRD → 通知相关人 → 才可开发。
- 与任总扣子版的差异点：v13 为全新自研实现，**只参考扣子版的目标效果（生成 UML、质检、输出图片），不继承其工作流与代码**。

## 3. 文档规范

- 文档目录与命名见 `02_编码与命名规范.md` 第 4 节。
- 每份文档必须有：版本号、编写人、日期、修订记录。
- 文档使用 Markdown；技术图用 ASCII / Mermaid；需正式汇报时输出 PDF/PPT。
- 文档是给"陈老师 / 任总 / 董事长"可展示的工程级文档，语言准确、结构清晰、避免内部黑话。

## 4. 设计规范

- 模块职责单一：一个 Agent 只做一件事（QA / PPT / 教案 / UML）。
- 所有外部依赖（模型、知识库、工具）通过接口隔离，便于替换。
- 新增功能优先复用 `app/chains`、`app/tools` 已有组件，禁止复制粘贴代码。
- 关键设计（UML 质检规则、RAG 检索链路）必须写成文档再实现。

## 5. 代码评审规范

- 每次合并必须经过评审；禁止绕过评审直接合入。
- 评审关注：正确性 / 安全性（注入、密钥、越权）/ 可读性 / 测试覆盖 / 是否符合规范。
- AI 辅助生成的代码**必须人工 review**，重点核对业务逻辑与边界条件。
- 评审意见必须闭环：提出 → 修改 → 确认 → 关闭。

## 6. 安全与数据规范

- 师生数据、教材内容仅用于校内教学场景；不得外传、不得用于模型训练（除非明确授权）。
- 密钥、Token、数据库口令一律放环境变量 / 配置文件，禁止硬编码进代码。
- 财务等敏感数据不属于本平台范围；若涉及需单独评审。
- 对外 API 必须做鉴权与限流；上传文件必须做类型与大小校验。

## 7. 验收与发布规范

- 每个模块按 `04-项目管理/02_验收标准与Demo脚本.md` 的验收标准执行。
- 发布前必须跑通：核心 Demo 链路（问答 → PPT/教案 → UML 生成 → 质检）+ 全部测试。
- 每次发布打 tag，记录版本号与变更说明。
