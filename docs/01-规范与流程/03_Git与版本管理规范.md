# Git 与版本管理规范（v13）

> 保证团队协作可追溯、可回滚、可评审。单人开发同样遵守（便于复盘与回溯）。

---

## 1. 分支模型

```
main            （稳定可发布版，仅允许合并已验收代码）
 └─ develop     （集成开发分支，日常合并点）
     ├─ feature/uml-agent      （功能分支：按模块开）
     ├─ feature/ppt-agent
     ├─ fix/xxx                （缺陷修复分支）
     └─ docs/xxx               （纯文档分支）
```

- `main`：任何时候保持可运行、可演示；直接合并只允许 `hotfix` 且需紧急发布。
- `develop`：日常开发合入点；功能分支从 `develop` 拉出，完成后合回 `develop`。
- 禁止直接在 `main` / `develop` 上提交代码。

## 2. 提交规范（Conventional Commits）

格式：`<type>(<scope>): <描述>`

| type | 含义 |
|---|---|
| feat | 新功能 |
| fix | 缺陷修复 |
| docs | 文档变更 |
| refactor | 重构（不改变行为） |
| test | 测试相关 |
| chore | 构建 / 依赖 / 杂项 |
| style | 格式调整（无逻辑变化） |

示例：
```
feat(uml): 增加边界检查规则（数据库不得作为参与者）
fix(qa): 修复知识库检索无结果时的兜底回答
docs: 更新 UML Agent PRD 验收标准
```

- 描述用中文，动词开头，简洁说明"做了什么"。
- 一次提交只做一件事；禁止 `feat: 一堆东西` 式大杂烩提交。

## 3. 提交信息规范

- 每个提交必须写清楚"为什么"（必要时在正文补充背景）。
- 提交前自查：`git status` 无多余文件；`git diff` 确认无密钥/临时文件。

## 4. 合并（PR / Merge Request）规范

- 功能完成 + 自测通过后提 PR 到 `develop`；PR 标题同提交规范。
- PR 描述必须包含：改动内容、测试情况、是否 AI 辅助生成、评审关注点。
- 至少 1 名其他开发者评审通过后才可合并；评审意见未闭环不得合并。
- 合并使用 squash（保持历史干净）；冲突解决优先与相关人确认。

## 5. 版本与标签

- 发布打 tag：`v13.1.0`（主版本.次版本.补丁）。
- 每次发布更新 `CHANGELOG.md`，记录：新增 / 修复 / 变更 / 已知问题。
- tag 对应 `main` 上的提交，禁止对中间提交打发布 tag。

## 6. 忽略与安全

- `.gitignore` 必须包含：`__pycache__/`、`*.pyc`、`.env`、`*.log`、`.venv/`、`data/`（教材原件不入库，只入库公开版本或路径引用）、`minutes/`、`temp_import/` 等。
- 教材 / 课程资料按授权范围入库：优先以路径 + 清单方式管理，原件不进 Git。
- 发现误提交敏感信息，立即移除并从历史中清理，同时报告。

## 7. 文档同步

- 文档变更（PRD / 技术方案 / 规范）走 `docs/` 分支或随功能 PR 一起提交，保证文档与代码同步。
- 目录索引（README）随新增文档更新。
